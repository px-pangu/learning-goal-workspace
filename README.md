# 学习目标管理台（WorkBuddy 资料库在线版）

管的是「有终点、有总量」的学习目标：背完 2000 个单词、读完一本 440 页的书。
不是「每天喝水」那种无期限习惯打卡 —— 每个目标都有**总量**和**截止日**，页面替你算今天该做多少、按当前速度来不来得及。

数据存在 WorkBuddy 资料库的数据表里（不是浏览器本地），换设备、换浏览器打开同一个链接，数据都在。

---

## 功能

四个 Tab：

| Tab | 内容 |
|---|---|
| **今日** | 新建目标入口；「今天要处理」区（红卡/黄卡）；可直接打卡的目标卡；底部再留一个醒目新建入口 |
| **看板** | 每个目标：进度环、完成率/连续天数/预计完成日、障碍预案、最近记录（可展开删除）；手写 SVG 的近 14 天投入分钟分目标堆叠柱状图 |
| **周报** | 按周一到周日汇总投入量/打卡天数/分钟数 + 上周同口径环比；可翻历史周；四栏复盘（保持/问题/尝试/下周预案）可保存；一键生成周报文本 |
| **我的** | 在线同步状态与最近同步时间、手动重新同步、清空示例、输入「清空」清空全部、添加到手机主屏幕的三步说明 |

其他：一天可记多笔；打卡可填分钟数（选填）；支持补记最近 6 天（带「补」标，按真实日期参与连续天数与推算）；目标达成时有彩带动效；图标全部内联 SVG，无 emoji、无外部资源；手机底部四 Tab 单列、平板顶部横向导航、桌面左侧固定边栏多栏布局。

## 核心规则

这些数字都是算出来的，不是拍的：

- **今日建议量** = 剩余量 ÷ 剩余天数（含今天），打卡时预填、允许修改
- **预计完成日** = 剩余量 ÷ 近 7 天日均速度 → 推算日期，再与截止日比出「提前 N 天 / 拖后 N 天」；**近 7 天没有记录就显示「暂无推算」，不编数字**
- **连续打卡** 每周允许 1 个休息日：本周第一次漏打卡不中断，第二次才断；休息日不计入连续天数
- **昨日漏打卡** 的目标今天自动置顶，并按情形给两张卡：**黄卡**（漏的那天用掉了本周休息日 → 连续天数保住）或**红卡**（没得抵 → 滚入今日；若同时已逾期，附「立即打卡」与「调整计划」两个出口）

## 数据表

| 数据表 | 用途 | 字段 |
|---|---|---|
| 学习目标 | 目标定义 | 目标名 / 单位 / 总量 / 截止日 / 创建日 / 配色 / 障碍 / 对策 / 示例 / 目标ID |
| 每日打卡记录 | 每次打卡一条 | 日期 / 目标名 / 打卡量 / 单位 / 分钟 / 补记 / 目标ID / 记录ID |
| 每周复盘 | 每周一条 | 周起始日 / 保持 / 问题 / 尝试 / 下周预案 / 示例 |

字段类型与取值格式见 [docs/data-schema.md](docs/data-schema.md)。

## 快速开始

页面**不绑定任何特定账号的数据表**：数据表 ID 由使用者自己配置，配谁的就读谁的。

1. 在你自己的 WorkBuddy 资料库里按上表建好三张数据表 —— 可以用脚本一次建齐：

```bash
python3 tools/init_tables.py --skill-dir <资料库skill目录> --dry-run   # 先看要建什么
python3 tools/init_tables.py --skill-dir <资料库skill目录>             # 建表并打印三个 ID
python3 tools/init_tables.py --skill-dir <资料库skill目录> --configure  # 建表并直接写进 index.html
```

2. 把三张表的 ID 配进页面（两种方式，任选其一，见下）
3. 把 `index.html` 导入你的资料库空间，导入时绑定这三张表
4. 打开页面即可

> 资料库目前没有「删除整张表」的接口，所以 `init_tables.py` 建出来的表需要你在资料库里手动删；建议先 `--dry-run`，确认表名与字段后再真建。

### 方式一：一键配置（推荐）

```bash
python3 tools/configure.py --goals <学习目标表ID> --logs <打卡记录表ID> --notes <每周复盘表ID>
```

脚本会改 `index.html` 顶部的配置区。想先看看当前配没配：

```bash
python3 tools/configure.py --check
```

### 方式二：页面内填写（不用碰代码）

打开页面 → 「我的」→ **数据表绑定**，把三个表 ID 粘进去保存，立即生效，存在本机浏览器里。

### 还没配置时是什么行为

- **不会**去请求任何表，更不会连到作者的表（`tools/binding_check.js` 有断言专门守这条）
- 页面照常可用，数据存在当前浏览器（localStorage），换设备不同步
- 首屏会明确提示「未绑定数据表」，不会假装在线

> 直接用浏览器双击打开 `index.html` 同样是这个行为：资料库运行时才会注入 `window.__SMART_PAGE__.database`。

## 数据可靠性

- **读取**：分页拉全量（`pageSize` 200，按 `nextCursor` 续拉，带循环保护）；先渲染界面再拉数据，不白屏
- **写入**：新建目标 / 打卡 / 补记 / 删除记录 / 保存复盘都即时写回；删除串行化，避免单表 QPS 限流
- **失败降级**：读取失败给「重试同步」入口并用本机缓存继续显示；写入失败先暂存本机，下次同步以「目标ID / 记录ID / 周起始日」为唯一键**幂等补写**；两种失败都有明确提示，不静默丢数据
- **跨端同步**：订阅数据表变更事件，1.2s 防抖后重新拉取

## 项目结构

```
index.html              交付页面（单文件，含全部 CSS / JS）
tools/configure.py      一键把三张表 ID 配进页面（--check 可查看当前配置）
tools/init_tables.py    在自己的资料库里一次建好三张表（--dry-run 可预览）
tools/gen_seed.py       生成示例数据载荷（按「今天」相对偏移，演示状态可复现）
tools/reseed.py         一键重置线上示例数据（只删带示例标记的行，你的数据不动）
tools/fetch_rows.py     把数据表读回的内容转成页面行结构（带类型）
tools/render_check.js   渲染回归校验（用页面自身的逻辑跑断言）
tools/offline_check.js  离线可用性自检（模拟无 SDK 环境启动 + 点击）
tools/binding_check.js  数据归属安全校验（证明只会读写配置给它的表）
docs/data-schema.md     三张数据表的字段定义
```

页面顶部有一个集中的**配置区**（`DB_GOALS` / `DB_LOGS` / `DB_NOTES`），三张表的 ID 只在这里出现一次；
SDK 调用统一从 `BINDING` 取值，因此改一处（或页面内填一次）就全生效。

## 开发与自检

```bash
# 1) 一键写示例数据（删旧示例 → 按今天重新生成 → 写回三张表；先 --dry-run 看影响面）
python3 tools/reseed.py --goals-table <目标表id> --logs-table <记录表id> --notes-table <复盘表id> \
    --skill-dir <资料库skill目录> --yes

# 2) 把表里的数据读回成页面行结构
python3 tools/fetch_rows.py --goals-table <id> --logs-table <id> --notes-table <id> \
    --skill-dir <资料库skill目录>

# 3) 渲染回归校验
node tools/render_check.js

# 4) 离线可用性自检（不需要任何数据表，clone 下来即可跑）
node tools/offline_check.js

# 5) 数据归属安全校验（同样不需要任何数据表）
node tools/binding_check.js
```

`offline_check.js` 回答的是「clone 下来、还没接任何数据表时，这页面能不能用」。它刻意把环境模拟成**没有 `window.__SMART_PAGE__` 的普通浏览器**，保留页面完整启动段跑真实启动流程，再用桩 DOM 模拟点击，验证离线模式下仍然：不白屏、能新建目标、能打卡、关掉重开数据还在、四个 Tab 能切。当前 **15/15 通过**。

`binding_check.js` 回答的是「它会不会读写到不该读写的表」。它桩掉 `window.__SMART_PAGE__.database` 并记录每一次调用的 `databaseId`：未配置时断言**一次调用都没有**；在「我的 → 数据表绑定」里填了 ID 后，断言请求只打到填的那几个 ID、不出现任何 22 位的他人表 ID。当前 **12/12 通过**。

### 已知取舍：静态校验 DSDK011

资料库的静态校验规则要求 `data-sp-database-id` 属性写成**字面量**，而支持运行时配置必然要把它写成表达式（属性值与 SDK 调用同源，来自同一个 `BINDING`，一致性反而比手写更可靠）。因此本页会稳定报 4 条 DSDK011，属有意取舍，不是缺陷；`PQ001` / `PQ005` 两条同为误报（脚本已通过 `node --check`，且全页 HTML 写入点唯一、插入前均经 `esc()` 转义）。

`render_check.js` 的做法值得说明：它**不重写一遍业务逻辑**（那样只是自证），而是把 `index.html` 里的内联脚本抽出来，切掉末尾启动段、把内部函数挂到 `window.__T`，再用桩 DOM / localStorage 驱动 `applyGoals → applyLogs → applyNotes → refreshAll` 这条**真实渲染路径**，最后断言渲染出来的 DOM。断言通过的含义是「表里存的数据在页面上确实呈现为预期状态」。当前示例数据下 **20/20 通过**。

`gen_seed.py` 生成的示例数据刻意覆盖了各种边界状态：3 个目标、35 条打卡记录、2 条周复盘，全部带 `示例` 标记；其中含**红卡**（逾期 + 昨天没学 + 近 7 天无记录 → 暂无推算）、**黄卡**（用掉本周休息日、连续天数保住）、2 条**补记**、2 条**未填分钟**（柱状图不硬凑）。日期全部相对「运行当天」计算，所以**不论星期几生成**，这几种状态都能复现。

> **示例数据会「过期」，这是设计使然**：日期是相对生成当天算的，因此「昨日漏打卡 → 红卡/黄卡」「近 7 天速度 → 预计完成日」这些状态只在**生成当天**成立。隔几天再跑 `render_check.js` 会出现 FAIL —— 那不是代码坏了，而是演示数据不再"新"。跑一次 `tools/reseed.py` 即可复原（重跑后回到 **20/20**）。

`reseed.py` 只删除带示例标记的行，你自己新增的目标 / 打卡 / 复盘不会被碰：

| 表 | 判定为示例的条件 |
|---|---|
| 学习目标 | `示例 = true`，或 `目标ID` 以 `seed-` 开头 |
| 每日打卡记录 | `记录ID` 以 `lg-` 开头，或 `目标ID` 以 `seed-` 开头 |
| 每周复盘 | `示例 = true` |

因此**「每周复盘」表需要 `示例` 这一列**（checkbox，页面自己不写它，只用于区分示例数据）；`docs/data-schema.md` 的字段定义已包含。旧表可以用资料库 skill 的 `add_database_field.py` 补一列，再把历史示例行更新为 `true`。
